\section{Containerization}

\subsection{What is a container?}

A container is a self-contained software environment that includes an application
together with the libraries, tools and runtime dependencies needed to execute it.
The main idea is to make the software reproducible and portable: instead of
installing all packages manually on every machine, one builds a container image
once and then runs it wherever a compatible container runtime is available.\\
\newline
A \textbf{container image} can be thought of as a frozen snapshot of a working software
environment. For example \texttt{fiTQun\_latest.sif}
is Apptainer image containing a predefined software setup.

\subsection{Docker and Apptainer}

Two common container tools are Docker and Apptainer.

\paragraph{Docker.}
Docker is widely used to build, distribute and run container images. Images are
usually written through a \texttt{Dockerfile} and can be downloaded from
registries such as Docker Hub or GitHub Container Registry.\\
For example:
\begin{lstlisting}[style=terminal]
docker pull wcsim/wcsim:latest
\end{lstlisting}
downloads a Docker image from Docker Hub.

\paragraph{Apptainer.}
Apptainer, formerly Singularity, is commonly used in HPC environments. It is
designed to run containers without requiring root privileges from the user. It
can run local \texttt{.sif} images and can also pull images from Docker-compatible
registries.\\
For example:
\begin{lstlisting}[style=terminal]
apptainer pull wcsim_latest.sif docker://wcsim/wcsim:latest
\end{lstlisting}
downloads a Docker image and converts it into an Apptainer \texttt{.sif} image.

\subsection{Where container images can be stored}

A container image is just a file. For Apptainer, the usual image format is
\texttt{.sif}. This means that the image can be stored:

\begin{itemize}
    \item on the local machine;
    \item on a remote server;
    \item in a shared filesystem accessible from several machines;
    \item in a project directory on a cluster.
\end{itemize}
If the image is stored on a shared filesystem, different users or different
compute nodes can run the same software environment without reinstalling it.

\subsection{Basic Apptainer commands}

\subsubsection{Check that Apptainer is available}

\begin{lstlisting}[style=terminal]
apptainer --version
\end{lstlisting}

\subsubsection{Run a command inside a container}

The most common command is \texttt{apptainer exec}. It runs a command inside the
container and then exits.

\begin{lstlisting}[style=terminal]
apptainer exec image.sif command
\end{lstlisting}
Example:
\begin{lstlisting}[style=terminal]
apptainer exec fiTQun_latest.sif which root
\end{lstlisting}
With an environment setup script:
\begin{lstlisting}[style=terminal]
apptainer exec fiTQun_latest.sif bash ./fiTQun_env.sh which runfiTQun
\end{lstlisting}
In this example, \texttt{fiTQun\_env.sh} sets the paths to fiTQun, ROOT and
WCSimRoot before executing the requested command.

\subsubsection{Open an interactive shell}

To enter the container interactively:

\begin{lstlisting}[style=terminal]
apptainer shell image.sif
\end{lstlisting}
Inside the shell, one can run commands as if working inside the container:
\begin{lstlisting}[style=terminal]
which root
which runfiTQun
which WCSim
\end{lstlisting}
To exit:
\begin{lstlisting}[style=terminal]
exit
\end{lstlisting}
However, one important point must be kept in mind: Apptainer usually binds the current working directory and the user
home directory from the host system into the container. Therefore, if the container is opened from a directory on the host machine, running \texttt{ls} show the content of the current host directory, not the internal software
directories of the container. Inside the shell, one can run \texttt{ls /} to look at the actual content of the container.
In the following a demonstrative example is shown:
\begin{lstlisting}[style=terminal]
[cc@marduk HyperKamiokande]$ ls
fiTQun_env.sh    fiTQun_latest.sif  fiTQun_WCSim.sif
fiTQun_git_repo  fiTQun_WCSim.def   utils
[cc@marduk HyperKamiokande]$ apptainer shell fiTQun_WCSim.sif
Apptainer> ls
fiTQun_env.sh	 fiTQun_latest.sif  fiTQun_WCSim.sif
fiTQun_git_repo  fiTQun_WCSim.def   utils
Apptainer> ls /
bin   dev	   etc	 lib	lost+found  mnt  proc  run   singularity  sys  usr
boot  environment  home  lib64	media	    opt  root  sbin  srv	  tmp  var
Apptainer> cd usr
bash: cd: usr: No such file or directory
Apptainer> cd /usr
\end{lstlisting}


\subsubsection{Pull an image from a registry}

Apptainer can pull images from Docker-compatible registries and convert them to
\texttt{.sif} format.\\
From Docker Hub:
\begin{lstlisting}[style=terminal]
apptainer pull wcsim_latest.sif docker://wcsim/wcsim:latest
\end{lstlisting}
From GitHub Container Registry:
\begin{lstlisting}[style=terminal]
apptainer pull hk_software.sif docker://ghcr.io/hyperk/hk-software:0.0.2
\end{lstlisting}
In the case of fiTQun:
\begin{lstlisting}[style=terminal]
apptainer pull namefile.sif docker://registry.git.hyperk.org/hyperk/recon/fitqun:latest
\end{lstlisting}

\subsubsection{Build an image from a definition file}

An Apptainer image can be built from a definition file:

\begin{lstlisting}[style=terminal]
apptainer build output_image.sif recipe.def
\end{lstlisting}
Example:
\begin{lstlisting}[style=terminal]
apptainer build fiTQun_WCSim.sif fiTQun_WCSim.def
\end{lstlisting}
The definition file describes the base image, the installation commands and the environment variables that should be available inside the final image.\\
On some systems, building an image may require root privileges because the build process has to install packages and write into system directories inside the container image. If the system supports user namespaces, Apptainer can emulate
this with:
\begin{lstlisting}[style=terminal]
apptainer build --fakeroot output_image.sif recipe.def
\end{lstlisting}
The option \texttt{--fakeroot} does not make the user root on the host machine, it only gives the build process root-like privileges inside the isolated build environment. This is useful, for example, when the definition file contains
commands such as:
\begin{lstlisting}[style=terminal]
yum install ...
apt-get install ...
mkdir /usr/local/hk/...
\end{lstlisting}
Without \texttt{--fakeroot}, these operations may fail if the user does not have the required permissions. Whether \texttt{--fakeroot} works depends on the configuration of the server or cluster.

\subsubsection{Inspect an image}

The command \texttt{apptainer inspect} is used to read metadata stored inside an image without opening an interactive shell.\\
The general command is:
\begin{lstlisting}[style=terminal]
apptainer inspect image.sif
\end{lstlisting}
This gives general information about the image. More specific options are often more useful.\\
To inspect the environment variables defined by the image:
\begin{lstlisting}[style=terminal]
apptainer inspect --environment image.sif
\end{lstlisting}
For example, in the registry fiTQun image this command may show variables related to fiTQun, ROOT and WCSimRoot. The clean WCSim image, instead, uses setup scripts under \texttt{/opt}. In this guide the runtime environment is therefore not inferred only from \texttt{apptainer inspect}; it is explicitly loaded with:
\begin{lstlisting}[style=terminal]
# WCSim image
source /opt/setup.sh
source /opt/WCSim/install/bin/this_wcsim.sh

# fiTQun image
bash fiTQun_WCSim_env.sh <command>
\end{lstlisting}
This is more transparent than relying on the container runscript, because it makes clear which software stack is being used in each step.\
To inspect the runscript:
\begin{lstlisting}[style=terminal]
apptainer inspect --runscript image.sif
\end{lstlisting}
However, in this workflow \texttt{apptainer exec} is preferred over \texttt{apptainer run}, because the commands explicitly source the required environment scripts before running WCSim or fiTQun.

\subsubsection{Bind host directories inside the container}
A container image contains the software environment, but input and output data are often stored outside the image. The \texttt{--bind} option is used to mount a directory from the host system inside the container.\\
The general syntax is:
\begin{lstlisting}[style=terminal]
apptainer exec --bind /host/path:/container/path image.sif command
\end{lstlisting}
Here:
\begin{itemize}
    \item \texttt{/host/path} is the directory on the real machine;
    \item \texttt{/container/path} is the path where that directory will appear
    inside the container.
\end{itemize}
For example:
\begin{lstlisting}[style=terminal]
apptainer exec \
    --bind /data/hk:/data/hk \
    fiTQun_WCSim.sif \
    bash /usr/local/hk/fiTQun_WCSim_env.sh \
    ls /data/hk
\end{lstlisting}
This makes the host directory \texttt{/data/hk} visible inside the container as \texttt{/data/hk}.\\
This is useful, for example, when WCSim output ROOT files are stored outside the container and one wants to process them with fiTQun inside the container:
\begin{lstlisting}[style=terminal]
apptainer exec \
    --bind /data/hk:/data/hk \
    fiTQun_WCSim.sif \
    bash /usr/local/hk/fiTQun_WCSim_env.sh \
    runfiTQun \
        -n 1 \
        -r /data/hk/fitqun_output.root \
        -p /path/to/HyperK.parameters.dat \
        /data/hk/wcsim_input.root
\end{lstlisting}
In this example:
\begin{itemize}
    \item the file \texttt{wcsim\_input.root} is physically stored on the host machine in \texttt{/data/hk};
    \item the container sees it as \texttt{/data/hk/wcsim\_input.root};
    \item fiTQun runs inside the container;
    \item the output file \texttt{fitqun\_output.root} is written back to the host directory.
\end{itemize}
One can also bind a directory to a different path inside the container:
\begin{lstlisting}[style=terminal]
apptainer exec \
    --bind /scratch/cc/hk_data:/data \
    fiTQun_WCSim.sif \
    bash /usr/local/hk/fiTQun_WCSim_env.sh \
    ls /data
\end{lstlisting}
Here, the host directory \texttt{/scratch/cc/hk\_data} appears inside the
container as \texttt{/data}.

\subsection{Practical remarks}
Container images should be treated as versioned software environments. If WCSim, fiTQun, ROOT or Geant4 are updated, a new image should be built and saved with a clear name, for example:
\begin{lstlisting}[style=terminal]
fitqun_plus_wcsim_test_v1.sif
fitqun_plus_wcsim_test_v2.sif
\end{lstlisting}
For reproducibility, it is useful to store a small text file inside or next to the image containing the relevant software versions:
\begin{lstlisting}[style=terminal]
ROOT version
Geant4 version
WCSim commit
fiTQun commit
WCSimRoot version
build date
\end{lstlisting}
This avoids ambiguity when results are produced at different times or on
different machines.

\section{WCSim}
\label{sec:wcsim}

\subsection{Purpose of WCSim}

WCSim is a Geant4-based simulation program for water Cherenkov detectors.
It is used to simulate the detector geometry, particle propagation, Cherenkov
light production, PMT response and detector-level output. Its main dependencies
are \texttt{ROOT} and \texttt{Geant4}. \textbf{The output is stored in ROOT files using
the WCSimRoot classes}, which can then be read by reconstruction software such
as fiTQun.\\
\newline
In the context of this work, WCSim is needed for event simulation, while fiTQun
is used for event reconstruction. This distinction is important: an installation
containing only WCSimRoot is sufficient for reading WCSim output files, but it is
not sufficient to generate new simulated events.

\subsection{WCSim CI workflows}
\label{WCSim_CI}
The WCSim repository uses GitHub Actions for build and physics validation tests.\\
The workflow \texttt{build\_and\_physics\_test.yml} runs inside the container:
\begin{lstlisting}[style=defstyle]
docker://ghcr.io/hyperk/hk-software:0.0.2
\end{lstlisting}
which provides the software prerequisites used by the automated tests. The
workflow then checks out the WCSim source code, checks out the separate
\href{https://github.com/WCSim/Validation}{WCSim Validation} repository, sets up the environment, installs additional packages such as HepMC3, builds WCSim, and runs the validation tests. In practice, the CI uses a
prepared base image containing the required dependencies and then builds the current WCSim source code inside it.\\
\textbf{This base image (\texttt{docker://ghcr.io/hyperk/hk-software:0.0.2)} is therefore the most relevant reference environment for WCSim}, since it is the one used by the current WCSim automated
build and validation workflow.
\subsection{Installation of WCSim}
The WCSim installation is therefore performed by closely following the most recent CI workflow used by the official WCSim repository, so that the local build reproduces as closely as possible the validated environment used for automated compilation and physics checks.
\subsubsection{Creating a writable WCSim build environment}
\label{subsec:wcsim_sandbox}

A convenient way to build and test the functionality of WCSim step by step is to create a writable Apptainer sandbox:
\begin{lstlisting}[style=terminal]
apptainer build --sandbox hk_wcsim_sandbox \
  docker://ghcr.io/hyperk/hk-software:0.0.2
\end{lstlisting}
Then enter the sandbox in writable mode:
\begin{lstlisting}[style=terminal]
apptainer shell --writable hk_wcsim_sandbox
\end{lstlisting}
Inside the sandbox, all subsequent commands are executed in the WCSim build environment.

\subsubsection{Installing the additional CI dependency HepMC3}
\label{subsec:install_hepmc3}

The WCSim CI workflow installs HepMC3 through \texttt{yum}. The same operation can be reproduced inside the sandbox:
\begin{lstlisting}[style=terminal]
cd /etc/yum.repos.d/

sed -i 's/mirrorlist/#mirrorlist/g' /etc/yum.repos.d/CentOS-*
sed -i 's|#baseurl=http://mirror.centos.org|baseurl=http://vault.centos.org|g' \
  /etc/yum.repos.d/CentOS-*

yum install -y \
  HepMC3 \
  HepMC3-devel \
  HepMC3-search \
  HepMC3-search-devel \
  HepMC3-interfaces-devel \
  HepMC3-doc
\end{lstlisting}
The two \texttt{sed} commands are needed because the base image uses CentOS repositories whose standard mirror configuration may no longer be directly reachable. Replacing the mirror list with the CentOS vault URLs makes \texttt{yum} able to resolve the packages.

\subsubsection{Preparing the WCSim prerequisite setup script}
\label{subsec:wcsim_prereq_setup}

The CI creates a setup script under \texttt{/opt/setup.sh}. The same logic is used here:
\begin{lstlisting}[style=terminal]
cd /opt

cat > /opt/setup.sh <<'EOF'
source /usr/local/hk/Geant4/install-Linux_x86_64-gcc_8-python_3.8.13/bin/geant4.sh
source /usr/local/hk/hk-pilot/setup.sh
source /usr/local/hk/hk-software/install-Linux_x86_64-gcc_8-python_3.8.13/setup.sh
EOF
\end{lstlisting}
The WCSim workflow also applies a small fix to the Hyper-K software setup script:
\begin{lstlisting}[style=terminal]
cd /usr/local/hk/hk-software/install-Linux_x86_64-gcc_8-python_3.8.13/
sed -i -e 's/LD_LIBRARY_PATH=LD_LIBRARY_PATH/LD_LIBRARY_PATH=$LD_LIBRARY_PATH/' setup.sh
\end{lstlisting}
After this, the environment is loaded with:
\begin{lstlisting}[style=terminal]
source /opt/setup.sh
\end{lstlisting}
Useful checks are:
\begin{lstlisting}[style=terminal]
which root
root-config --version
which geant4-config
geant4-config --version
\end{lstlisting}
which should return the ROOT and Geant4 installations from \texttt{/usr/local/hk}.

\subsubsection{Geant4 data variables}
\label{subsec:wcsim_geant4_data}

The Geant4 setup script defines the data variables needed by the physics lists. They should be checked before building and running WCSim:
\begin{lstlisting}[style=terminal]
echo "G4LEDATA=$G4LEDATA"
echo "G4NEUTRONHPDATA=$G4NEUTRONHPDATA"
echo "G4NEUTRONXSDATA=$G4NEUTRONXSDATA"
echo "G4RADIOACTIVEDATA=$G4RADIOACTIVEDATA"
echo "G4REALSURFACEDATA=$G4REALSURFACEDATA"
echo "G4ENSDFSTATEDATA=$G4ENSDFSTATEDATA"

ls "$G4LEDATA" | head
ls "$G4NEUTRONHPDATA" | head
ls "$G4NEUTRONXSDATA" | head
\end{lstlisting}
The variable \texttt{G4NEUTRONXSDATA} is especially important for the neutron elastic cross-section data. If it is missing, Geant4 can stop with:
\begin{lstlisting}[style=terminal]
G4Exception : had013
issued by : G4NeutronElasticXS::Initialise(..)
Environment variable G4NEUTRONXSDATA is not defined
\end{lstlisting}
In the clean WCSim build environment, it points to:
\begin{lstlisting}[style=terminal]
/usr/local/hk/Geant4/install-Linux_x86_64-gcc_8-python_3.8.13/share/Geant4-10.3.3/data/G4NEUTRONXS1.4
\end{lstlisting}

\subsubsection{Building and installing WCSim}
\label{subsec:wcsim_build_install}

The WCSim source code is cloned under \texttt{/opt/WCSim/src}. The build and install directories are kept separate:
\begin{lstlisting}[style=terminal]
source /opt/setup.sh

cd /opt
mkdir -p /opt/WCSim

git clone https://github.com/WCSim/WCSim.git /opt/WCSim/src
cd /opt/WCSim/src
git checkout develop
git rev-parse HEAD
\end{lstlisting}
In the tested build, the checked-out commit was:
\begin{lstlisting}[style=terminal]
5be124b35a5832bc1d90466169acc581d8b6fbd7
\end{lstlisting}
The build is then performed with CMake:
\begin{lstlisting}[style=terminal]
cd /opt/WCSim
mkdir -p build install
cd build

/usr/bin/cmake ../src \
  -D CMAKE_INSTALL_PREFIX=/opt/WCSim/install

make -j$(nproc)
make install
\end{lstlisting}
The explicit path \texttt{/usr/bin/cmake} is used to avoid accidentally calling a broken Python wrapper called \texttt{cmake} from \texttt{/root/.local/bin}. If the wrong executable is used, the configuration can fail with:
\begin{lstlisting}[style=terminal]
ModuleNotFoundError: No module named 'cmake'
\end{lstlisting}
The step \texttt{make install} is essential. Before this step, the WCSim executable may exist only in the build directory, while the installation directory is still empty. After installation, the relevant files are available under:
\begin{lstlisting}[style=terminal]
/opt/WCSim/install/bin/WCSim
/opt/WCSim/install/bin/this_wcsim.sh
/opt/WCSim/install/data/CathodeParameters.txt
/opt/WCSim/install/macros/jobOptions.mac
/opt/WCSim/install/mPMT-configfiles/mPMTconfig_19_nuPrism_3ring.txt
/opt/WCSim/install/lib/cmake/WCSim/WCSimConfig.cmake
\end{lstlisting}

\subsubsection{WCSim runtime setup}
\label{subsec:wcsim_runtime_setup}

The installed WCSim setup script is:
\begin{lstlisting}[style=terminal]
/opt/WCSim/install/bin/this_wcsim.sh
\end{lstlisting}
It defines:
\begin{lstlisting}[style=terminal]
export WCSIM_BUILD_DIR=/opt/WCSim/install/
export ROOT_INCLUDE_PATH=/opt/WCSim/install/include/WCSim:$ROOT_INCLUDE_PATH
export PATH=/opt/WCSim/install/bin:$PATH
export LD_LIBRARY_PATH=/opt/WCSim/install/lib:$LD_LIBRARY_PATH
export WCSIM_SOURCE_DIR=/opt/WCSim/src/
\end{lstlisting}
A minimal runtime check is:
\begin{lstlisting}[style=terminal]
source /opt/setup.sh
source /opt/WCSim/install/bin/this_wcsim.sh

echo "WCSIM_BUILD_DIR=$WCSIM_BUILD_DIR"
echo "WCSIM_SOURCE_DIR=$WCSIM_SOURCE_DIR"
which WCSim

ls "$WCSIM_BUILD_DIR/macros/jobOptions.mac"
ls "$WCSIM_BUILD_DIR/mPMT-configfiles/mPMTconfig_19_nuPrism_3ring.txt"
ls "$WCSIM_BUILD_DIR/data/CathodeParameters.txt"
\end{lstlisting}

\subsection{Build WCSim image directly from a docker file}
\label{subsec:wcsim_sif}

After the sandbox has been built and checked, it can be converted into a read-only Apptainer image:
\begin{lstlisting}[style=terminal]
apptainer build hk_wcsim_clean.sif hk_wcsim_sandbox
\end{lstlisting}
or directly defining a docker file with all the installation procedures described in the previous sections and proceed to the building with:
\begin{lstlisting}[style=terminal]
apptainer build WCSim.sif WCSim.def
\end{lstlisting}
The docker file is included in Appendix \ref{Appendix_B}.\\
It contains also a \texttt{\%runscript} section. This defines the default command executed when the container is launched with \texttt{apptainer run}. In this case, it is used to automatically load the WCSim runtime environment, move to the WCSim installation directory, and forward all user-provided command-line arguments to the \texttt{WCSim} executable.

\subsection{Running WCSim}
\label{subsec:running_wcsim}
To run WCSim, the host directory containing the user macro must be bind-mounted inside the container. The output directory must also be bind-mounted to the same container path used in the macro. For example, if the macro writes the output file to \texttt{/output\_data}, as in
\begin{lstlisting}[style=defstyle]
## change the name of the output root file, default = wcsim.root
/WCSimIO/RootFile /output_data/wcsim_HK_muplus_michel.root
\end{lstlisting}
then the host output directory has to be bound to \texttt{/output\_data} when running the container.\\
For instance, from a directory containing the image, a macros directory called \texttt{WCSim\_macros} and a \texttt{work\_data} folder, the run command is:
\begin{lstlisting}[style=terminal]
apptainer run \
  --bind "$(pwd)"/WCSim_macros:/working_macros \
  --bind "$(pwd)/work_data":/output_data \
  WCSim.sif \
  /working_macros/muplus_michel_HK.mac \
  /opt/WCSim/install/macros/tuning_parameters_hkfd.mac
\end{lstlisting}
where \texttt{muplus\_michel\_HK.mac} is the user-defined macro, \texttt{tuning\_parameters\_hkfd.mac} is the default tuning parameter macro.
\subsubsection{Tuning parameter macro}
The tuning-parameter macro must also be passed explicitly to WCSim as a second argument. This file defines detector-level tuning parameters, such as water attenuation, Rayleigh scattering, cathode reflectivity, blacksheet reflection, and veto settings. If the default Hyper-K far detector tuning is used, the file can be taken directly from the WCSim installation inside the container:
\begin{lstlisting}[style=defstyle]
/opt/WCSim/install/macros/tuning_parameters_hkfd.mac
\end{lstlisting}
If this file needs to be modified, a custom version should be placed on the host system and bind-mounted inside the container, exactly as done for the user macro.
\subsubsection{WCSim macro}
The WCSim macro controls the detector geometry, PMT quantum efficiency, DAQ, dark noise, particle generator and output file. For the realistic Hyper-K ID-only geometry, the macro should contain:
\begin{lstlisting}[style=terminal]
/WCSim/WCgeom HyperK_HybridmPMT_IDonly_Realistic
/WCSim/Construct
\end{lstlisting}
The old geometry name:
\begin{lstlisting}[style=terminal]
/WCSim/WCgeom HyperK
\end{lstlisting}
is obsolete in the new WCSim build and causes WCSim to exit. WCSim explicitly suggests using one of the newer geometries, for example:
\begin{lstlisting}[style=terminal]
HyperK_HybridmPMT_WithOD_Realistic
HyperK_HybridmPMT_IDonly_Realistic
\end{lstlisting}
For the realistic Hyper-K geometry, the PMT quantum-efficiency method must be:
\begin{lstlisting}[style=terminal]
/WCSim/PMTQEMethod SensitiveDetector_Only
\end{lstlisting}
The older option:
\begin{lstlisting}[style=terminal]
/WCSim/PMTQEMethod Stacking_Only
\end{lstlisting}
is rejected by WCSim for this configuration.\\
A simple particle-gun setup for a positive muon is:

\section{fiTQun}
\label{sec:fitqun}

\subsection{Purpose of fiTQun}

fiTQun is a likelihood-based reconstruction package for water Cherenkov detectors. It reconstructs event-level quantities such as vertex position, particle direction, momentum, number of rings and particle identification. In this workflow, fiTQun is not used to simulate events. It reads WCSim ROOT files and reconstructs them.\\
The final workflow adopted here uses two separate images:
\begin{itemize}
    \item a dedicated WCSim image, built from the Hyper-K software base image and used only for event generation;
    \item a dedicated fiTQun image, derived from the official Hyper-K registry image and used only for reconstruction.
\end{itemize}
This separation avoids mixing two different software stacks in the same container and makes the role of each image clearer.
\subsection{Installation of fiTQun}
\subsubsection{Using the official fiTQun registry image}
\label{subsec:fitqun_registry_image}

\begin{lstlisting}[style=defstyle]

\end{lstlisting}

\begin{lstlisting}[style=terminal]

\subsubsection{Building a derived fiTQun image}
\label{subsec:fitqun_derived_image}

Instead of running the registry image directly with a long command, a derived Apptainer image is built. The goal is not to rebuild fiTQun itself, but to make the runtime environment cleaner and more reproducible. The derived image:
\begin{itemize}
    \item keeps the fiTQun installation from the official registry image;
    \item defines a small runtime setup script inside the image;
    \item downloads the Hyper-K tuning constants directly into the standard fiTQun constants directory;
    \item defines a \texttt{\%runscript} so that \texttt{apptainer run} automatically launches \texttt{runfiTQun}.
\end{itemize}
The runtime setup script is written during the build as:
\begin{lstlisting}[style=defstyle]
cat > /opt/setup_fitqun.sh <<'EOF'
#!/bin/bash

export FITQUN_ROOT=/usr/local/hk/fiTQun

export ROOT_INSTALL=/usr/local/hk/ROOT/install-Linux_x86_64-gcc_8-python_3.12.1
export FITQUN_INSTALL=/usr/local/hk/fiTQun/install-Linux_x86_64-gcc_8-python_3.12.1
export WCSIMROOT_INSTALL=/usr/local/hk/WCSimRoot/install-Linux_x86_64-gcc_8-python_3.12.1
export TOOLFRAMEWORKCORE_INSTALL=/usr/local/hk/ToolFrameworkCore/install-Linux_x86_64-gcc_8-python_3.12.1

export PATH="$ROOT_INSTALL/bin:$FITQUN_INSTALL/bin:$PATH"

export LD_LIBRARY_PATH="$ROOT_INSTALL/lib:$FITQUN_INSTALL/lib:$WCSIMROOT_INSTALL/lib:$TOOLFRAMEWORKCORE_INSTALL/lib:${LD_LIBRARY_PATH:-}"

export ROOT_INCLUDE_PATH="$WCSIMROOT_INSTALL/include/WCSimRoot:${ROOT_INCLUDE_PATH:-}"
EOF

chmod +x /opt/setup_fitqun.sh
\end{lstlisting}
The script manually defines the relevant paths instead of sourcing the full ROOT setup script. This is intentional: in the tested image, the ROOT setup script refers to a Geant4 installation path that is not present in the image. Defining the paths explicitly avoids this inconsistency and keeps the runtime environment minimal.\\
\newline
The \texttt{\%runscript} is:
\begin{lstlisting}[style=defstyle]
%runscript
    set -eo pipefail

    source /opt/setup_fitqun.sh

    exec runfiTQun "$@"
\end{lstlisting}
The runscript acts as the default command executed by \texttt{apptainer run}. It loads the fiTQun runtime environment and then forwards all user-provided arguments to the \texttt{runfiTQun} executable. It does not hard-code the input file, output file, number of events or parameter override file.

\section{Structure of WCSim ROOT files}
\label{sec:wcsim_object_hierarchy}

WCSim stores the simulated detector response in a ROOT file. The output is not a
flat ntuple where each branch directly corresponds to a simple physics variable.
Instead, the main event tree stores C++ objects, and the event information must
be accessed through the WCSim ROOT classes.\\
The most relevant trees are usually

\begin{lstlisting}[language=C++]
wcsimT
wcsimGeoT
wcsimRootOptionsT
\end{lstlisting}
The tree \texttt{wcsimT} contains the event information. The tree
\texttt{wcsimGeoT} contains the detector geometry, while
\texttt{wcsimRootOptionsT} stores the simulation options.\\
A ROOT file can be inspected with

\begin{lstlisting}[language=C++]
TFile *f = TFile::Open("wcsim_output.root");
f->ls();

TTree *t = (TTree*) f->Get("wcsimT");
t->Print();
\end{lstlisting}
or in PyROOT with
\begin{lstlisting}[language=python]
import ROOT

f = ROOT.TFile.Open("wcsim_output.root")
f.ls()

tree = f.Get("wcsimT")
tree.Print()
\end{lstlisting}
The command \texttt{f->ls()} shows the top-level objects stored in the file.
The command \texttt{tree->Print()} shows the branch structure of the selected
tree.

\subsection{Global Structure of the Event Tree}

For the geometry

\begin{lstlisting}[language=C++]
/WCSim/WCgeom HyperK_HybridmPMT_WithOD_Realistic
\end{lstlisting}
the event tree \texttt{wcsimT} contains three main event branches:

\begin{lstlisting}[language=C++]
wcsimrootevent
wcsimrootevent2
wcsimrootevent_OD
\end{lstlisting}
Each of these branches stores a \texttt{WCSimRootEvent} object. The meaning of the three branches is
\begin{center}
\begin{tabular}{lll}
\hline
ROOT branch & WCSim detector element & Physical meaning \\
\hline
\texttt{wcsimrootevent} &
\texttt{tank} &
Inner Detector, main 20-inch Box\&Line PMTs \\

\texttt{wcsimrootevent2} &
\texttt{tankPMT2} &
Inner Detector, multi-PMT system \\

\texttt{wcsimrootevent\_OD} &
\texttt{OD} &
Outer Detector PMT system \\
\hline
\end{tabular}
\end{center}
The word ``hybrid'' means that the Inner Detector contains two PMT systems: the
main 20-inch PMTs and the mPMT modules. Therefore,
\texttt{wcsimrootevent2} is not a raw-hit branch and it is not a duplicate of
\texttt{wcsimrootevent}. It is the \texttt{WCSimRootEvent} branch associated
with the mPMT system.\\
The conceptual file hierarchy is
\begin{lstlisting}
ROOT file
|
|-- wcsimT
|   |
|   |-- entry 0
|   |   |
|   |   |-- wcsimrootevent       WCSimRootEvent for main ID PMTs
|   |   |-- wcsimrootevent2      WCSimRootEvent for ID mPMTs
|   |   `-- wcsimrootevent_OD    WCSimRootEvent for OD PMTs
|   |
|   |-- entry 1
|   |   |
|   |   |-- wcsimrootevent
|   |   |-- wcsimrootevent2
|   |   `-- wcsimrootevent_OD
|   |
|   `-- ...
|
|-- wcsimGeoT
|
`-- wcsimRootOptionsT
\end{lstlisting}
Thus, each entry of \texttt{wcsimT} contains one \texttt{WCSimRootEvent} object
for each detector branch.

\subsection{Reading a Branch: Meaning of \texttt{SetBranchAddress}}

Opening the tree does not automatically load the content of an event branch into
a Python or C++ object. ROOT must first be told where to place the content of the
branch when an entry is read. This is the purpose of \texttt{SetBranchAddress}.\\
In C++, one writes for example

\begin{lstlisting}[language=C++]
WCSimRootEvent *event = new WCSimRootEvent();
tree->SetBranchAddress("wcsimrootevent", &event);
\end{lstlisting}
This connects the branch named \texttt{wcsimrootevent} to the memory address of
the pointer \texttt{event}. After this connection has been made, the instruction
\begin{lstlisting}
tree->GetEntry(ientry);
\end{lstlisting}
loads entry \texttt{ientry} from the tree and fills the \texttt{WCSimRootEvent}
object with the content of the branch \texttt{wcsimrootevent}.\\
In PyROOT, the analogous pattern is
\begin{lstlisting}[language=python]
event = ROOT.WCSimRootEvent()
tree.SetBranchAddress("wcsimrootevent", event)

tree.GetEntry(ientry)
\end{lstlisting}
After \texttt{tree.GetEntry(ientry)}, the object \texttt{event} contains the
\texttt{WCSimRootEvent} stored in that entry of the selected branch.\\
The same logic can be used for the three detector branches:

\begin{lstlisting}[language=python]
event_main = ROOT.WCSimRootEvent()
event_mpmt = ROOT.WCSimRootEvent()
event_od   = ROOT.WCSimRootEvent()

tree.SetBranchAddress("wcsimrootevent",    event_main)
tree.SetBranchAddress("wcsimrootevent2",   event_mpmt)
tree.SetBranchAddress("wcsimrootevent_OD", event_od)

tree.GetEntry(ientry)
\end{lstlisting}
After \texttt{GetEntry}, the three objects contain the event information for the
main ID PMTs, the ID mPMTs, and the OD PMTs, respectively.

\subsection{From \texttt{WCSimRootEvent} to \texttt{WCSimRootTrigger}}

A \texttt{WCSimRootEvent} is not itself a single PMT hit, a single particle, or
even necessarily a single trigger. It is a container of trigger objects.\\
The number of trigger objects stored in the current event branch is obtained with
\begin{lstlisting}[language=python]
event.GetNumberOfEvents()
\end{lstlisting}
The trigger object with index \texttt{i} is obtained with
\begin{lstlisting}[language=python]
trigger = event.GetTrigger(i)
\end{lstlisting}
The object returned by \texttt{GetTrigger(i)} is a
\texttt{WCSimRootTrigger}.
Therefore, the object hierarchy is
\begin{lstlisting}
TTree entry
|
`-- WCSimRootEvent
    |
    |-- GetNumberOfEvents()
    |
    `-- GetTrigger(i)
        |
        `-- WCSimRootTrigger
            |
            |-- true tracks
            |-- true PMT hits
            |-- true photon hit-times
            |-- digitized PMT hits
            `-- trigger-level information
\end{lstlisting}
The methods
\begin{lstlisting}[language=python]
GetNumberOfEvents()
HasSubEvents()
GetTrigger(i)
\end{lstlisting}
belong to the \texttt{WCSimRootEvent} object.\\
The methods
\begin{lstlisting}[language=python]
GetNtrack()
GetTracks()
GetNcherenkovhits()
GetCherenkovHits()
GetNcherenkovhittimes()
GetCherenkovHitTimes()
GetNcherenkovdigihits()
GetCherenkovDigiHits()
GetTriggerType()
GetTriggerInfo()
\end{lstlisting}
belong to the \texttt{WCSimRootTrigger} object.\\
\newline
A typical PyROOT loop is
\begin{lstlisting}[language=python]
event = ROOT.WCSimRootEvent()
tree.SetBranchAddress("wcsimrootevent", event)

for ientry in range(tree.GetEntries()):
    tree.GetEntry(ientry)

    ntriggers = event.GetNumberOfEvents()

    for itrigger in range(ntriggers):
        trigger = event.GetTrigger(itrigger)

        print("entry:", ientry)
        print("trigger:", itrigger)
        print("N tracks:", trigger.GetNtrack())
        print("N digi hits:", trigger.GetNcherenkovdigihits())
\end{lstlisting}
The method \texttt{event.GetTrigger(i)} can only be called on a
\texttt{WCSimRootEvent}. The returned object is the corresponding
\texttt{WCSimRootTrigger}.

\subsection{Trigger Objects and Subevents}

The quantity
\begin{lstlisting}
event.GetNumberOfEvents()
\end{lstlisting}
gives the number of \texttt{WCSimRootTrigger} objects stored inside the current
\texttt{WCSimRootEvent}.\\
For example,
\begin{lstlisting}[language=python]
event.GetNumberOfEvents() = 1
event.HasSubEvents()      = False
\end{lstlisting}
means that the selected tree entry contains one trigger object in that detector
branch.\\
The method
\begin{lstlisting}
event.HasSubEvents()
\end{lstlisting}
is true when more than one trigger object is present.\\
This WCSim trigger structure should not be confused with the subevent finding
performed later by reconstruction algorithms such as fiTQun. WCSim stores
trigger windows and digitized PMT hits according to the DAQ and trigger
configuration. Reconstruction algorithms may later split the digitized hits into
time subevents for fitting purposes.

\subsection{The Four Main Information Levels Inside a Trigger}

Inside a \texttt{WCSimRootTrigger}, the information is organized into four main
levels:

\begin{center}
\begin{tabular}{lll}
\hline
Level & WCSim method & Main question answered \\
\hline
True particles &
\texttt{GetTracks()} &
Which particles existed in the simulation? \\

True PMT hits &
\texttt{GetCherenkovHits()} &
Which PMTs received true photons/PEs? \\

True photon times &
\texttt{GetCherenkovHitTimes()} &
Which individual photons arrived, when, and from which parent? \\

Digitized PMT hits &
\texttt{GetCherenkovDigiHits()} &
What did the simulated electronics record? \\
\hline
\end{tabular}
\end{center}
This distinction is essential. The track collection is particle-level truth
information. The Cherenkov hit and hit-time collections are PMT-level truth
information before digitization. The digi-hit collection is detector-level
information after the electronics response.

```latex
\subsection{True Particle Tracks: \texttt{GetTracks()}}

The true particle tracks stored in a WCSim trigger are accessed with
\begin{lstlisting}[language=python]
tracks = trigger.GetTracks()
ntracks = trigger.GetNtrack()
\end{lstlisting}
The object \texttt{tracks} is a \texttt{TClonesArray} of
\texttt{WCSimRootTrack} objects. Individual tracks are accessed with
\texttt{At(i)}:
\begin{lstlisting}[language=python]
tracks = trigger.GetTracks()

for itrack in range(trigger.GetNtrack()):
    track = tracks.At(itrack)

    ipnu = track.GetIpnu()
    parent_type = track.GetParenttype()

    track_id = track.GetId()
    parent_id = track.GetParentId()
    creator = track.GetCreatorProcessName()

    mass = track.GetM()
    p = track.GetP()
    E = track.GetE()
    K = E - mass

    start = [
        track.GetStart(0),
        track.GetStart(1),
        track.GetStart(2),
    ]

    stop = [
        track.GetStop(0),
        track.GetStop(1),
        track.GetStop(2),
    ]

    direction = [
        track.GetDir(0),
        track.GetDir(1),
        track.GetDir(2),
    ]

    time = track.GetTime()
\end{lstlisting}
The most useful methods are:
\begin{itemize}
    \item \texttt{GetIpnu()}: PDG code of the particle.
    \item \texttt{GetId()}: unique Geant4/WCSim track ID. This is the ID to use
    for truth matching.
    \item \texttt{GetParentId()}: unique track ID of the parent particle.
    \item \texttt{GetParenttype()}: PDG code of the parent particle, when WCSim
    can identify it. A value of \texttt{0} usually indicates a primary particle,
    while \texttt{999} means that the parent PDG code was not found by the
    specific WCSim logic used to fill this variable.
    \item \texttt{GetCreatorProcessName()}: Geant4 process that created the
    track, for example \texttt{initial}, \texttt{Decay}, \texttt{compt},
    \texttt{phot}, \texttt{conv}, etc.
    \item \texttt{GetM()}, \texttt{GetP()}, \texttt{GetE()}: particle mass,
    initial momentum and initial total energy, in MeV units.
    \item \texttt{GetStart(i)} and \texttt{GetStop(i)}: start and stop positions
    of the track, in cm.
    \item \texttt{GetDir(i)}: initial direction unit vector.
    \item \texttt{GetTime()}: start time of the track, in ns.
\end{itemize}
\textbf{Importat note: which particles are saved in \texttt{WCSim} tracks}\\
The \texttt{GetTracks()} collection is not the full Geant4 truth history. It is a reduced list of
\texttt{WCSimRootTrack} objects selected by WCSim. In particular, by default
optical Cherenkov photons are not saved as entries in \texttt{GetTracks()}.
The exception is not optical light, but Geant4 ``gamma'' particles, i.e. high
energy photons, when they are saved by a specific part of the WCSim output
logic.\\
The tracks saved by WCSim include:
\begin{itemize}
    \item primary particles;
    \item particles whose PDG code belongs to the WCSim tracking
    \texttt{ParticleList}, such as \(e^-\), \(e^+\), \(\mu^-\), \(\mu^+\),
    pions, kaons, protons and neutrons;
    \item particles produced by selected Geant4 processes in the WCSim
    \texttt{ProcessList}, such as decays, conversions (only $\gamma\to e^+e^-$), $\mu^-$ captures, optical wavelength shifting (optical photon absorption and re-emission of the same photon at different wavelength) and neutron captures;
    \item particles which produced a Cherenkov photon that produced a true PMT
    hit, together with their ancestors.
\end{itemize}
Therefore, the presence of a track in \texttt{GetTracks()} does not imply that
this particle produced light observed by the PMTs. For example, in a low-energy
positron event, the positron may annihilate after stopping:
\[
    e^+ + e^- \rightarrow \gamma + \gamma .
\]
The annihilation gammas can travel through the detector and produce secondary
electrons by Compton scattering or photoelectric interactions. These secondary
electrons can appear in \texttt{GetTracks()} with
\texttt{GetCreatorProcessName()} equal to \texttt{compt} or \texttt{phot}, even
if they are below Cherenkov threshold and produce no PMT hit. In such a case,
\texttt{parent\_id} can point to a gamma track which was present in Geant4 but
not saved in the \texttt{WCSimRootTrack} array. This is one common reason why
\texttt{GetParenttype()} can be \texttt{999}.\\
\newline
\textbf{Last warning}: note that all the particles tracks are unique for all the event triggers, so they are stored only inside the first trigger object even if the collection contain particles whose hits are associated with a different trigger.

\subsection{True PMT Hits: \texttt{GetCherenkovHits()}}

The true PMT hits before digitization are accessed with

\begin{lstlisting}[language=python]
true_hits = trigger.GetCherenkovHits()
nhits = trigger.GetNcherenkovhits()
\end{lstlisting}
The object \texttt{true\_hits} is a \texttt{TClonesArray} of
\texttt{WCSimRootCherenkovHit} objects.\\
A \texttt{WCSimRootCherenkovHit} is not a single photon. It is a record
associated with one PMT that received at least one true photon or photoelectron
before digitization.\\
For each \texttt{WCSimRootCherenkovHit}, the important methods are

\begin{lstlisting}[language=python]
hit.GetTubeID()
hit.GetTotalPe(0)
hit.GetTotalPe(1)
\end{lstlisting}
Their meaning is:

\begin{itemize}
    \item \texttt{GetTubeID()} gives the PMT tube ID.
    \item \texttt{GetTotalPe(0)} gives the starting position, inside the
    trigger-wide array returned by \texttt{GetCherenkovHitTimes()}, of the
    individual true photon hits associated with this PMT.
    \item \texttt{GetTotalPe(1)} gives the number of individual true photons/PEs
    associated with this PMT.
\end{itemize}
Thus, \texttt{GetCherenkovHits()} gives the list of PMTs that were hit, while
\texttt{GetCherenkovHitTimes()} gives the detailed list of the individual true
photons/PEs.\\
\newline
A typical loop starts as
\begin{lstlisting}[language=python]
true_hits = trigger.GetCherenkovHits()

for ihit in range(trigger.GetNcherenkovhits()):
    hit = true_hits.At(ihit)

    tube_id = hit.GetTubeID()
    first_index = hit.GetTotalPe(0)
    n_photons = hit.GetTotalPe(1)
\end{lstlisting}
At this stage, \texttt{hit} identifies the PMT and tells where to find the
individual photons associated with that PMT.

\subsection{True Photon Hit-Times: \texttt{GetCherenkovHitTimes()}}

The individual true photon or photoelectron entries are stored in

\begin{lstlisting}[language=python]
true_times = trigger.GetCherenkovHitTimes()
ntimes = trigger.GetNcherenkovhittimes()
\end{lstlisting}
The object \texttt{true\_times} is a \texttt{TClonesArray} of
\texttt{WCSimRootCherenkovHitTime} objects.
Unlike \texttt{WCSimRootCherenkovHit}, which is PMT-level, a
\texttt{WCSimRootCherenkovHitTime} is photon-level or photoelectron-level truth
information. It stores information about one individual true hit contribution.\\
Important methods are
\begin{lstlisting}[language=python]
hit_time.GetTruetime()
hit_time.GetParentID()
\end{lstlisting}
where

\begin{itemize}
    \item \texttt{GetTruetime()} gives the true arrival time of that photon/PE;
    \item \texttt{GetParentID()} gives the identifier of the true parent particle
    that produced that photon/PE.
\end{itemize}
The relation between \texttt{CherenkovHits} and \texttt{CherenkovHitTimes} is
therefore
\begin{itemize}
\item \texttt{trigger.GetCherenkovHits()}: list of PMTs with true hits
\item \texttt{trigger.GetCherenkovHitTimes()}:
one trigger-wide list of all individual true photons/PEs
\end{itemize}
The word ``trigger-wide'' means that there is one common
\texttt{CherenkovHitTimes} array for the whole \texttt{WCSimRootTrigger}, not a
separate array for each PMT.\\
For example, suppose the true photons in a trigger are
\begin{lstlisting}
PMT 10 receives 2 true photons
PMT 25 receives 1 true photon
PMT 80 receives 3 true photons
\end{lstlisting}
WCSim stores the PMT-level objects as

\begin{lstlisting}
CherenkovHits:
  hit 0 -> PMT 10, first_index = 0, n_photons = 2
  hit 1 -> PMT 25, first_index = 2, n_photons = 1
  hit 2 -> PMT 80, first_index = 3, n_photons = 3
\end{lstlisting}
and the individual photon-level objects as one trigger-wide array:

\begin{lstlisting}
CherenkovHitTimes:
  index 0 -> photon on PMT 10
  index 1 -> photon on PMT 10
  index 2 -> photon on PMT 25
  index 3 -> photon on PMT 80
  index 4 -> photon on PMT 80
  index 5 -> photon on PMT 80
\end{lstlisting}
Therefore, if
\begin{lstlisting}
hit.GetTubeID()    = 80
hit.GetTotalPe(0) = 3
hit.GetTotalPe(1) = 3
\end{lstlisting}
then PMT 80 has three true photons, stored in \texttt{CherenkovHitTimes} at
indices 3, 4 and 5.\\
\newline
A complete PMT-to-photon loop is

\begin{lstlisting}[language=python]
true_hits = trigger.GetCherenkovHits()
true_times = trigger.GetCherenkovHitTimes()

for ihit in range(trigger.GetNcherenkovhits()):
    hit = true_hits.At(ihit)

    tube_id = hit.GetTubeID()
    first_index = hit.GetTotalPe(0)
    n_photons = hit.GetTotalPe(1)

    print("PMT:", tube_id)
    print("Number of true photons:", n_photons)

    for k in range(n_photons):
        hit_time = true_times.At(first_index + k)

        true_time = hit_time.GetTruetime()
        parent_id = hit_time.GetParentID()

        print("  photon:", k)
        print("    true time:", true_time)
        print("    parent ID:", parent_id)
\end{lstlisting}
This loop answers the question:

\begin{center}
\emph{For each PMT, which individual true photons arrived, at what time, and
from which true particle?}
\end{center}

\subsection{Parent ID and Connection to True Particles}

The method

\begin{lstlisting}
hit_time.GetParentID()
\end{lstlisting}
is the key method for tracing PMT light back to the particle that produced it.
It gives the identifier of the true parent particle associated with the
individual photon/PE.\\
The conceptual chain is
\begin{lstlisting}
PMT-level true hit
|
|-- hit.GetTubeID()
|       -> which PMT was hit
|
|-- hit.GetTotalPe(0), hit.GetTotalPe(1)
|       -> where the photons of this PMT are stored
|
v
photon-level true hit-time
|
|-- hit_time.GetTruetime()
|       -> when this photon arrived
|
`-- hit_time.GetParentID()
        -> which true particle produced this photon
\end{lstlisting}
In a muon plus Michel electron event, this is the information needed to ask
whether a PMT received light from the muon, from the decay electron, or from
both.\\
The track collection and the hit-time collection play different roles:

\begin{itemize}
    \item \texttt{GetTracks()} gives the true particles and their kinematics.
    \item \texttt{GetCherenkovHitTimes()} gives the true photon-level
    contributions and their parent IDs.
\end{itemize}
Therefore, the tracks identify the particles, while the hit-times identify which
particle contributed light to each PMT.

\subsection{Digitized PMT Hits: \texttt{GetCherenkovDigiHits()}}

The previous collections describe truth-level information before digitization.
The digitized detector response is accessed with

\begin{lstlisting}
digi_hits = trigger.GetCherenkovDigiHits()
ndigi = trigger.GetNcherenkovdigihits()
\end{lstlisting}
The object \texttt{digi\_hits} is a \texttt{TClonesArray} of
\texttt{WCSimRootCherenkovDigiHit} objects.\\
A digitized hit is the PMT signal after the WCSim electronics and digitization
stage. The most important methods are
\begin{lstlisting}
digi_hit.GetTubeId()
digi_hit.GetQ()
digi_hit.GetT()
\end{lstlisting}
where
\begin{itemize}
    \item \texttt{GetTubeId()} gives the digitized PMT ID;
    \item \texttt{GetQ()} gives the digitized charge;
    \item \texttt{GetT()} gives the digitized time.
\end{itemize}
The digitized collection answers the question:

\begin{center}
\emph{What did the simulated electronics record for each PMT?}
\end{center}
This is the collection most directly related to trigger studies and to
reconstruction algorithms.\\
The distinction between
\begin{lstlisting}
trigger.GetNcherenkovdigihits()
trigger.GetNumDigiTubesHit()
\end{lstlisting}
is the following:
\begin{itemize}
    \item \texttt{GetNcherenkovdigihits()} counts the number of digitized hit
    objects stored in the trigger.
    \item \texttt{GetNumDigiTubesHit()} counts the number of PMT tubes with at
    least one digitized hit.
\end{itemize}
If
\begin{lstlisting}
GetNcherenkovdigihits() = 208
GetNumDigiTubesHit()   = 208
\end{lstlisting}
then the trigger contains one digitized hit per digitized PMT. If multiple digitized hits per PMT per trigger were stored, one could instead have
\begin{lstlisting}
GetNcherenkovdigihits() > GetNumDigiTubesHit()
\end{lstlisting}

\subsection{From a Digitized Hit Back to True Photons}

A digitized hit does not by itself directly say ``this signal came from the
muon'' or ``this signal came from the Michel electron''. It gives the detector
response: PMT ID, charge and time.\\
However, WCSim can store the connection between a digitized hit and the true
photons that contributed to it. This connection is accessed through
\begin{lstlisting}
digi_hit.GetPhotonIds()
\end{lstlisting}
The method \texttt{GetPhotonIds()} returns indices in the trigger-wide
\texttt{CherenkovHitTimes} array. These indices point to the individual true
photon/PE entries that contributed to the digitized hit.\\
The full chain is

\begin{lstlisting}
WCSimRootCherenkovDigiHit
|
|-- GetTubeId()
|       -> digitized PMT ID
|
|-- GetQ()
|       -> digitized charge
|
|-- GetT()
|       -> digitized time
|
`-- GetPhotonIds()
        -> indices in CherenkovHitTimes
             |
             v
        WCSimRootCherenkovHitTime
             |
             |-- GetTruetime()
             `-- GetParentID()
                    |
                    v
              true parent particle
\end{lstlisting}
A conceptual PyROOT loop is

\begin{lstlisting}[language=python]
from collections import Counter

true_times = trigger.GetCherenkovHitTimes()
digi_hits = trigger.GetCherenkovDigiHits()

for idigi in range(trigger.GetNcherenkovdigihits()):
    digi_hit = digi_hits.At(idigi)

    tube_id = digi_hit.GetTubeId()
    q = digi_hit.GetQ()
    t = digi_hit.GetT()

    photon_ids = digi_hit.GetPhotonIds()

    parent_counter = Counter()

    for j in range(photon_ids.size()):
        hit_time_index = photon_ids[j]
        hit_time = true_times.At(hit_time_index)

        parent_id = hit_time.GetParentID()
        parent_counter[parent_id] += 1

    print("digitized PMT:", tube_id)
    print("digitized charge:", q)
    print("digitized time:", t)
    print("true parent contributions:", parent_counter)
\end{lstlisting}
This loop answers the question:

\begin{center}
\emph{For this digitized PMT hit, which true photons contributed to it, and from
which true particles did they originate?}
\end{center}
This is especially useful when a PMT receives light from more than one particle.
For example, in a muon plus Michel electron event, a digitized PMT hit may
contain contributions from both the primary muon and the decay electron. The
digitized charge is then a detector-level mixture of the two truth-level light
contributions.

\subsection{Example: Interpreting Raw and Digitized Counts}

Consider the following output:

\begin{lstlisting}[language=python]
event.GetNumberOfEvents() = 1
event.HasSubEvents()      = False

Trigger object 0
  GetNtrack()                  = 44
  GetNcherenkovhits()          = 532
  GetNcherenkovhittimes()      = 540
  GetNumTubesHit()             = 532
  GetNcherenkovdigihits()      = 208
  GetNumDigiTubesHit()         = 208
  GetTriggerType()             = 0
  GetTriggerInfo().size()      = 3

TriggerInfo values:
  [0] = 43.0
  [1] = 950.0
  [2] = 160.5
\end{lstlisting}
The interpretation is:

\begin{itemize}
    \item The \texttt{WCSimRootEvent} contains one trigger object.
    \item \texttt{HasSubEvents()} is false because there is not more than one
    trigger object in the event branch.
    \item The trigger contains 44 true tracks.
    \item There are 532 PMTs/tubes with true hits before digitization.
    \item There are 540 individual true hit-time entries. Since this is larger
    than 532, at least some PMTs received more than one true photon/PE.
    \item There are 208 digitized hit objects after the electronics response.
    \item There are also 208 digitized PMTs, so in this trigger there is one
    digitized hit per digitized PMT.
\end{itemize}
Physically, the event contains more true PMT activity than digitized PMT
activity. This is expected. Not every true photon-level contribution survives the
detector response, thresholding, electronics simulation and trigger-window
selection.

\subsection{Failed or Dummy Trigger Objects}

The presence of a \texttt{WCSimRootTrigger} object does not always guarantee that
the event contains useful digitized Cherenkov light. Depending on the WCSim
configuration, trigger failures or dummy trigger objects may be saved. Such
objects can have little or no digitized activity.\\
For this reason, an analysis should not rely only on the existence of a trigger
object. It should also check quantities such as

\begin{lstlisting}[language=python]
trigger.GetTriggerType()
trigger.GetNcherenkovdigihits()
trigger.GetNumDigiTubesHit()
trigger.GetSumQ()
\end{lstlisting}
A practical filter is
\begin{lstlisting}[language=python]
if trigger.GetNcherenkovdigihits() == 0:
    continue

if trigger.GetNumDigiTubesHit() == 0:
    continue
\end{lstlisting}
and, when necessary, an additional selection on \texttt{GetTriggerType()} should
be applied according to the trigger configuration used in the WCSim macro.

\subsection{Practical Summary}

The object hierarchy can be summarized as follows:

\begin{lstlisting}
ROOT file
|
`-- wcsimT
    |
    `-- tree entry
        |
        `-- WCSimRootEvent
            |
            `-- WCSimRootTrigger
                |
                |-- GetTracks()
                |     -> true particles
                |
                |-- GetCherenkovHits()
                |     -> PMTs with true hits before digitization
                |
                |-- GetCherenkovHitTimes()
                |     -> individual true photons/PEs,
                |        with true time and parent ID
                |
                `-- GetCherenkovDigiHits()
                      -> digitized PMT signals,
                         with charge and time
\end{lstlisting}
The most important conceptual distinctions are:

\begin{itemize}
    \item A \texttt{WCSimRootEvent} is read from a branch of \texttt{wcsimT}.
    \item A \texttt{WCSimRootTrigger} is obtained from a
    \texttt{WCSimRootEvent} using \texttt{GetTrigger(i)}.
    \item A \texttt{WCSimRootTrack} describes a true simulated particle.
    \item A \texttt{WCSimRootCherenkovHit} describes one PMT that received true
    light before digitization.
    \item A \texttt{WCSimRootCherenkovHitTime} describes one individual true
    photon/PE contribution and stores its parent ID.
    \item A \texttt{WCSimRootCherenkovDigiHit} describes the digitized signal
    recorded by the simulated electronics.
\end{itemize}
Therefore, to identify the true particles in the event, one uses

\begin{lstlisting}
trigger.GetTracks()
\end{lstlisting}
To know which PMTs received true light from which particles, one uses

\begin{lstlisting}
trigger.GetCherenkovHits()
trigger.GetCherenkovHitTimes()
hit_time.GetParentID()
\end{lstlisting}
To know which true photons contributed to a digitized PMT hit, one uses

\begin{lstlisting}
trigger.GetCherenkovDigiHits()
digi_hit.GetPhotonIds()
trigger.GetCherenkovHitTimes()
hit_time.GetParentID()
\end{lstlisting}
In a muon plus Michel electron event, this is the complete truth chain needed to
separate the PMT light contribution of the primary muon from that of the decay
electron.
