\section{Containerization}

\subsection{What is a container?}

A container is a self-contained software environment that includes an application
together with the libraries, tools and runtime dependencies needed to execute it.
The main idea is to make the software reproducible and portable: instead of
installing all packages manually on every machine, one builds a container image
once and then runs it wherever a compatible container runtime is available.\\
\newline
A \textbf{container image} can be thought of as a frozen snapshot of a working software
environment. For example \texttt{fiTQun\_latest.sif}
is Apptainer image containing a predefined software setup.

\subsection{Docker and Apptainer}

Two common container tools are Docker and Apptainer.

\paragraph{Docker.}
Docker is widely used to build, distribute and run container images. Images are
usually written through a \texttt{Dockerfile} and can be downloaded from
registries such as Docker Hub or GitHub Container Registry.\\
For example:
\begin{lstlisting}[style=terminal]
docker pull wcsim/wcsim:latest
\end{lstlisting}
downloads a Docker image from Docker Hub.

\paragraph{Apptainer.}
Apptainer, formerly Singularity, is commonly used in HPC environments. It is
designed to run containers without requiring root privileges from the user. It
can run local \texttt{.sif} images and can also pull images from Docker-compatible
registries.\\
For example:
\begin{lstlisting}[style=terminal]
apptainer pull wcsim_latest.sif docker://wcsim/wcsim:latest
\end{lstlisting}
downloads a Docker image and converts it into an Apptainer \texttt{.sif} image.

\subsection{Where container images can be stored}

A container image is just a file. For Apptainer, the usual image format is
\texttt{.sif}. This means that the image can be stored:

\begin{itemize}
    \item on the local machine;
    \item on a remote server;
    \item in a shared filesystem accessible from several machines;
    \item in a project directory on a cluster.
\end{itemize}
If the image is stored on a shared filesystem, different users or different
compute nodes can run the same software environment without reinstalling it.

\subsection{Basic Apptainer commands}

\subsubsection{Check that Apptainer is available}

\begin{lstlisting}[style=terminal]
apptainer --version
\end{lstlisting}

\subsubsection{Run a command inside a container}

The most common command is \texttt{apptainer exec}. It runs a command inside the
container and then exits.

\begin{lstlisting}[style=terminal]
apptainer exec image.sif command
\end{lstlisting}
Example:
\begin{lstlisting}[style=terminal]
apptainer exec fiTQun_latest.sif which root
\end{lstlisting}
With an environment setup script:
\begin{lstlisting}[style=terminal]
apptainer exec fiTQun_latest.sif bash ./fiTQun_env.sh which runfiTQun
\end{lstlisting}
In this example, \texttt{fiTQun\_env.sh} sets the paths to fiTQun, ROOT and
WCSimRoot before executing the requested command.

\subsubsection{Open an interactive shell}

To enter the container interactively:

\begin{lstlisting}[style=terminal]
apptainer shell image.sif
\end{lstlisting}
Inside the shell, one can run commands as if working inside the container:
\begin{lstlisting}[style=terminal]
which root
which runfiTQun
which WCSim
\end{lstlisting}
To exit:
\begin{lstlisting}[style=terminal]
exit
\end{lstlisting}
However, one important point must be kept in mind: Apptainer usually binds the current working directory and the user
home directory from the host system into the container. Therefore, if the container is opened from a directory on the host machine, running \texttt{ls} show the content of the current host directory, not the internal software
directories of the container. Inside the shell, one can run \texttt{ls /} to look at the actual content of the container.
In the following a demonstrative example is shown:
\begin{lstlisting}[style=terminal]
[cc@marduk HyperKamiokande]$ ls
fiTQun_env.sh    fiTQun_latest.sif  fiTQun_WCSim.sif
fiTQun_git_repo  fiTQun_WCSim.def   utils
[cc@marduk HyperKamiokande]$ apptainer shell fiTQun_WCSim.sif
Apptainer> ls
fiTQun_env.sh	 fiTQun_latest.sif  fiTQun_WCSim.sif
fiTQun_git_repo  fiTQun_WCSim.def   utils
Apptainer> ls /
bin   dev	   etc	 lib	lost+found  mnt  proc  run   singularity  sys  usr
boot  environment  home  lib64	media	    opt  root  sbin  srv	  tmp  var
Apptainer> cd usr
bash: cd: usr: No such file or directory
Apptainer> cd /usr
\end{lstlisting}


\subsubsection{Pull an image from a registry}

Apptainer can pull images from Docker-compatible registries and convert them to
\texttt{.sif} format.\\
From Docker Hub:
\begin{lstlisting}[style=terminal]
apptainer pull wcsim_latest.sif docker://wcsim/wcsim:latest
\end{lstlisting}
From GitHub Container Registry:
\begin{lstlisting}[style=terminal]
apptainer pull hk_software.sif docker://ghcr.io/hyperk/hk-software:0.0.2
\end{lstlisting}
In the case of fiTQun:
\begin{lstlisting}[style=terminal]
apptainer pull namefile.sif docker://registry.git.hyperk.org/hyperk/recon/fitqun:latest
\end{lstlisting}

\subsubsection{Build an image from a definition file}

An Apptainer image can be built from a definition file:

\begin{lstlisting}[style=terminal]
apptainer build output_image.sif recipe.def
\end{lstlisting}
Example:
\begin{lstlisting}[style=terminal]
apptainer build fiTQun_WCSim.sif fiTQun_WCSim.def
\end{lstlisting}
The definition file describes the base image, the installation commands and the environment variables that should be available inside the final image.\\
On some systems, building an image may require root privileges because the build process has to install packages and write into system directories inside the container image. If the system supports user namespaces, Apptainer can emulate
this with:
\begin{lstlisting}[style=terminal]
apptainer build --fakeroot output_image.sif recipe.def
\end{lstlisting}
The option \texttt{--fakeroot} does not make the user root on the host machine, it only gives the build process root-like privileges inside the isolated build environment. This is useful, for example, when the definition file contains
commands such as:
\begin{lstlisting}[style=terminal]
yum install ...
apt-get install ...
mkdir /usr/local/hk/...
\end{lstlisting}
Without \texttt{--fakeroot}, these operations may fail if the user does not have the required permissions. Whether \texttt{--fakeroot} works depends on the configuration of the server or cluster.

\subsubsection{Inspect an image}

The command \texttt{apptainer inspect} is used to read metadata stored inside an image without opening an interactive shell.\\
The general command is:
\begin{lstlisting}[style=terminal]
apptainer inspect image.sif
\end{lstlisting}
This gives general information about the image. More specific options are often more useful.\\
To inspect the environment variables defined by the image:
\begin{lstlisting}[style=terminal]
apptainer inspect --environment image.sif
\end{lstlisting}
For example, in the registry fiTQun image this command may show variables related to fiTQun, ROOT and WCSimRoot. The clean WCSim image, instead, uses setup scripts under \texttt{/opt}. In this guide the runtime environment is therefore not inferred only from \texttt{apptainer inspect}; it is explicitly loaded with:
\begin{lstlisting}[style=terminal]
# WCSim image
source /opt/setup.sh
source /opt/WCSim/install/bin/this_wcsim.sh

# fiTQun image
bash fiTQun_WCSim_env.sh <command>
\end{lstlisting}
This is more transparent than relying on the container runscript, because it makes clear which software stack is being used in each step.\
To inspect the runscript:
\begin{lstlisting}[style=terminal]
apptainer inspect --runscript image.sif
\end{lstlisting}
However, in this workflow \texttt{apptainer exec} is preferred over \texttt{apptainer run}, because the commands explicitly source the required environment scripts before running WCSim or fiTQun.

\subsubsection{Bind host directories inside the container}
A container image contains the software environment, but input and output data are often stored outside the image. The \texttt{--bind} option is used to mount a directory from the host system inside the container.\\
The general syntax is:
\begin{lstlisting}[style=terminal]
apptainer exec --bind /host/path:/container/path image.sif command
\end{lstlisting}
Here:
\begin{itemize}
    \item \texttt{/host/path} is the directory on the real machine;
    \item \texttt{/container/path} is the path where that directory will appear
    inside the container.
\end{itemize}
For example:
\begin{lstlisting}[style=terminal]
apptainer exec \
    --bind /data/hk:/data/hk \
    fiTQun_WCSim.sif \
    bash /usr/local/hk/fiTQun_WCSim_env.sh \
    ls /data/hk
\end{lstlisting}
This makes the host directory \texttt{/data/hk} visible inside the container as \texttt{/data/hk}.\\
This is useful, for example, when WCSim output ROOT files are stored outside the container and one wants to process them with fiTQun inside the container:
\begin{lstlisting}[style=terminal]
apptainer exec \
    --bind /data/hk:/data/hk \
    fiTQun_WCSim.sif \
    bash /usr/local/hk/fiTQun_WCSim_env.sh \
    runfiTQun \
        -n 1 \
        -r /data/hk/fitqun_output.root \
        -p /path/to/HyperK.parameters.dat \
        /data/hk/wcsim_input.root
\end{lstlisting}
In this example:
\begin{itemize}
    \item the file \texttt{wcsim\_input.root} is physically stored on the host machine in \texttt{/data/hk};
    \item the container sees it as \texttt{/data/hk/wcsim\_input.root};
    \item fiTQun runs inside the container;
    \item the output file \texttt{fitqun\_output.root} is written back to the host directory.
\end{itemize}
One can also bind a directory to a different path inside the container:
\begin{lstlisting}[style=terminal]
apptainer exec \
    --bind /scratch/cc/hk_data:/data \
    fiTQun_WCSim.sif \
    bash /usr/local/hk/fiTQun_WCSim_env.sh \
    ls /data
\end{lstlisting}
Here, the host directory \texttt{/scratch/cc/hk\_data} appears inside the
container as \texttt{/data}.

\subsection{Practical remarks}
Container images should be treated as versioned software environments. If WCSim, fiTQun, ROOT or Geant4 are updated, a new image should be built and saved with a clear name, for example:
\begin{lstlisting}[style=terminal]
fitqun_plus_wcsim_test_v1.sif
fitqun_plus_wcsim_test_v2.sif
\end{lstlisting}
For reproducibility, it is useful to store a small text file inside or next to the image containing the relevant software versions:
\begin{lstlisting}[style=terminal]
ROOT version
Geant4 version
WCSim commit
fiTQun commit
WCSimRoot version
build date
\end{lstlisting}
This avoids ambiguity when results are produced at different times or on
different machines.

\section{WCSim}
\label{sec:wcsim}

\subsection{Purpose of WCSim}

WCSim is a Geant4-based simulation program for water Cherenkov detectors.
It is used to simulate the detector geometry, particle propagation, Cherenkov
light production, PMT response and detector-level output. Its main dependencies
are \texttt{ROOT} and \texttt{Geant4}. \textbf{The output is stored in ROOT files using
the WCSimRoot classes}, which can then be read by reconstruction software such
as fiTQun.\\
\newline
In the context of this work, WCSim is needed for event simulation, while fiTQun
is used for event reconstruction. This distinction is important: an installation
containing only WCSimRoot is sufficient for reading WCSim output files, but it is
not sufficient to generate new simulated events.

\subsection{WCSim CI workflows}
\label{WCSim_CI}
The WCSim repository uses GitHub Actions for build and physics validation tests.\\
The workflow \texttt{build\_and\_physics\_test.yml} runs inside the container:
\begin{lstlisting}[style=defstyle]
docker://ghcr.io/hyperk/hk-software:0.0.2
\end{lstlisting}
which provides the software prerequisites used by the automated tests. The
workflow then checks out the WCSim source code, checks out the separate
\href{https://github.com/WCSim/Validation}{WCSim Validation} repository, sets up the environment, installs additional packages such as HepMC3, builds WCSim, and runs the validation tests. In practice, the CI uses a
prepared base image containing the required dependencies and then builds the current WCSim source code inside it.\\
\textbf{This base image (\texttt{docker://ghcr.io/hyperk/hk-software:0.0.2)} is therefore the most relevant reference environment for WCSim}, since it is the one used by the current WCSim automated
build and validation workflow.
\subsection{Installation of WCSim}
The WCSim installation is therefore performed by closely following the most recent CI workflow used by the official WCSim repository, so that the local build reproduces as closely as possible the validated environment used for automated compilation and physics checks.
\subsubsection{Creating a writable WCSim build environment}
\label{subsec:wcsim_sandbox}

A convenient way to build and test the functionality of WCSim step by step is to create a writable Apptainer sandbox:
\begin{lstlisting}[style=terminal]
apptainer build --sandbox hk_wcsim_sandbox \
  docker://ghcr.io/hyperk/hk-software:0.0.2
\end{lstlisting}
Then enter the sandbox in writable mode:
\begin{lstlisting}[style=terminal]
apptainer shell --writable hk_wcsim_sandbox
\end{lstlisting}
Inside the sandbox, all subsequent commands are executed in the WCSim build environment.

\subsubsection{Installing the additional CI dependency HepMC3}
\label{subsec:install_hepmc3}

The WCSim CI workflow installs HepMC3 through \texttt{yum}. The same operation can be reproduced inside the sandbox:
\begin{lstlisting}[style=terminal]
cd /etc/yum.repos.d/

sed -i 's/mirrorlist/#mirrorlist/g' /etc/yum.repos.d/CentOS-*
sed -i 's|#baseurl=http://mirror.centos.org|baseurl=http://vault.centos.org|g' \
  /etc/yum.repos.d/CentOS-*

yum install -y \
  HepMC3 \
  HepMC3-devel \
  HepMC3-search \
  HepMC3-search-devel \
  HepMC3-interfaces-devel \
  HepMC3-doc
\end{lstlisting}
The two \texttt{sed} commands are needed because the base image uses CentOS repositories whose standard mirror configuration may no longer be directly reachable. Replacing the mirror list with the CentOS vault URLs makes \texttt{yum} able to resolve the packages.

\subsubsection{Preparing the WCSim prerequisite setup script}
\label{subsec:wcsim_prereq_setup}

The CI creates a setup script under \texttt{/opt/setup.sh}. The same logic is used here:
\begin{lstlisting}[style=terminal]
cd /opt

cat > /opt/setup.sh <<'EOF'
source /usr/local/hk/Geant4/install-Linux_x86_64-gcc_8-python_3.8.13/bin/geant4.sh
source /usr/local/hk/hk-pilot/setup.sh
source /usr/local/hk/hk-software/install-Linux_x86_64-gcc_8-python_3.8.13/setup.sh
EOF
\end{lstlisting}
The WCSim workflow also applies a small fix to the Hyper-K software setup script:
\begin{lstlisting}[style=terminal]
cd /usr/local/hk/hk-software/install-Linux_x86_64-gcc_8-python_3.8.13/
sed -i -e 's/LD_LIBRARY_PATH=LD_LIBRARY_PATH/LD_LIBRARY_PATH=$LD_LIBRARY_PATH/' setup.sh
\end{lstlisting}
After this, the environment is loaded with:
\begin{lstlisting}[style=terminal]
source /opt/setup.sh
\end{lstlisting}
Useful checks are:
\begin{lstlisting}[style=terminal]
which root
root-config --version
which geant4-config
geant4-config --version
\end{lstlisting}
which should return the ROOT and Geant4 installations from \texttt{/usr/local/hk}.

\subsubsection{Geant4 data variables}
\label{subsec:wcsim_geant4_data}

The Geant4 setup script defines the data variables needed by the physics lists. They should be checked before building and running WCSim:
\begin{lstlisting}[style=terminal]
echo "G4LEDATA=$G4LEDATA"
echo "G4NEUTRONHPDATA=$G4NEUTRONHPDATA"
echo "G4NEUTRONXSDATA=$G4NEUTRONXSDATA"
echo "G4RADIOACTIVEDATA=$G4RADIOACTIVEDATA"
echo "G4REALSURFACEDATA=$G4REALSURFACEDATA"
echo "G4ENSDFSTATEDATA=$G4ENSDFSTATEDATA"

ls "$G4LEDATA" | head
ls "$G4NEUTRONHPDATA" | head
ls "$G4NEUTRONXSDATA" | head
\end{lstlisting}
The variable \texttt{G4NEUTRONXSDATA} is especially important for the neutron elastic cross-section data. If it is missing, Geant4 can stop with:
\begin{lstlisting}[style=terminal]
G4Exception : had013
issued by : G4NeutronElasticXS::Initialise(..)
Environment variable G4NEUTRONXSDATA is not defined
\end{lstlisting}
In the clean WCSim build environment, it points to:
\begin{lstlisting}[style=terminal]
/usr/local/hk/Geant4/install-Linux_x86_64-gcc_8-python_3.8.13/share/Geant4-10.3.3/data/G4NEUTRONXS1.4
\end{lstlisting}

\subsubsection{Building and installing WCSim}
\label{subsec:wcsim_build_install}

The WCSim source code is cloned under \texttt{/opt/WCSim/src}. The build and install directories are kept separate:
\begin{lstlisting}[style=terminal]
source /opt/setup.sh

cd /opt
mkdir -p /opt/WCSim

git clone https://github.com/WCSim/WCSim.git /opt/WCSim/src
cd /opt/WCSim/src
git checkout develop
git rev-parse HEAD
\end{lstlisting}
In the tested build, the checked-out commit was:
\begin{lstlisting}[style=terminal]
5be124b35a5832bc1d90466169acc581d8b6fbd7
\end{lstlisting}
The build is then performed with CMake:
\begin{lstlisting}[style=terminal]
cd /opt/WCSim
mkdir -p build install
cd build

/usr/bin/cmake ../src \
  -D CMAKE_INSTALL_PREFIX=/opt/WCSim/install

make -j$(nproc)
make install
\end{lstlisting}
The explicit path \texttt{/usr/bin/cmake} is used to avoid accidentally calling a broken Python wrapper called \texttt{cmake} from \texttt{/root/.local/bin}. If the wrong executable is used, the configuration can fail with:
\begin{lstlisting}[style=terminal]
ModuleNotFoundError: No module named 'cmake'
\end{lstlisting}
The step \texttt{make install} is essential. Before this step, the WCSim executable may exist only in the build directory, while the installation directory is still empty. After installation, the relevant files are available under:
\begin{lstlisting}[style=terminal]
/opt/WCSim/install/bin/WCSim
/opt/WCSim/install/bin/this_wcsim.sh
/opt/WCSim/install/data/CathodeParameters.txt
/opt/WCSim/install/macros/jobOptions.mac
/opt/WCSim/install/mPMT-configfiles/mPMTconfig_19_nuPrism_3ring.txt
/opt/WCSim/install/lib/cmake/WCSim/WCSimConfig.cmake
\end{lstlisting}

\subsubsection{WCSim runtime setup}
\label{subsec:wcsim_runtime_setup}

The installed WCSim setup script is:
\begin{lstlisting}[style=terminal]
/opt/WCSim/install/bin/this_wcsim.sh
\end{lstlisting}
It defines:
\begin{lstlisting}[style=terminal]
export WCSIM_BUILD_DIR=/opt/WCSim/install/
export ROOT_INCLUDE_PATH=/opt/WCSim/install/include/WCSim:$ROOT_INCLUDE_PATH
export PATH=/opt/WCSim/install/bin:$PATH
export LD_LIBRARY_PATH=/opt/WCSim/install/lib:$LD_LIBRARY_PATH
export WCSIM_SOURCE_DIR=/opt/WCSim/src/
\end{lstlisting}
A minimal runtime check is:
\begin{lstlisting}[style=terminal]
source /opt/setup.sh
source /opt/WCSim/install/bin/this_wcsim.sh

echo "WCSIM_BUILD_DIR=$WCSIM_BUILD_DIR"
echo "WCSIM_SOURCE_DIR=$WCSIM_SOURCE_DIR"
which WCSim

ls "$WCSIM_BUILD_DIR/macros/jobOptions.mac"
ls "$WCSIM_BUILD_DIR/mPMT-configfiles/mPMTconfig_19_nuPrism_3ring.txt"
ls "$WCSIM_BUILD_DIR/data/CathodeParameters.txt"
\end{lstlisting}

\subsection{Build WCSim image directly from a docker file}
\label{subsec:wcsim_sif}

After the sandbox has been built and checked, it can be converted into a read-only Apptainer image:
\begin{lstlisting}[style=terminal]
apptainer build hk_wcsim_clean.sif hk_wcsim_sandbox
\end{lstlisting}
or directly defining a docker file with all the installation procedures described in the previous sections and proceed to the building with:
\begin{lstlisting}[style=terminal]
apptainer build WCSim.sif WCSim.def
\end{lstlisting}
The docker file is included in Appendix \ref{Appendix_B}.\\
It contains also a \texttt{\%runscript} section. This defines the default command executed when the container is launched with \texttt{apptainer run}. In this case, it is used to automatically load the WCSim runtime environment, move to the WCSim installation directory, and forward all user-provided command-line arguments to the \texttt{WCSim} executable.

\subsection{Running WCSim}
\label{subsec:running_wcsim}
To run WCSim, the host directory containing the user macro must be bind-mounted inside the container. The output directory must also be bind-mounted to the same container path used in the macro. For example, if the macro writes the output file to \texttt{/output\_data}, as in
\begin{lstlisting}[style=defstyle]
## change the name of the output root file, default = wcsim.root
/WCSimIO/RootFile /output_data/wcsim_HK_muplus_michel.root
\end{lstlisting}
then the host output directory has to be bound to \texttt{/output\_data} when running the container.\\
For instance, from a directory containing the image, a macros directory called \texttt{WCSim\_macros} and a \texttt{work\_data} folder, the run command is:
\begin{lstlisting}[style=terminal]
apptainer run \
  --bind "$(pwd)"/WCSim_macros:/working_macros \
  --bind "$(pwd)/work_data":/output_data \
  WCSim.sif \
  /working_macros/muplus_michel_HK.mac \
  /opt/WCSim/install/macros/tuning_parameters_hkfd.mac
\end{lstlisting}
where \texttt{muplus\_michel\_HK.mac} is the user-defined macro, \texttt{tuning\_parameters\_hkfd.mac} is the default tuning parameter macro.
\subsubsection{Tuning parameter macro}
The tuning-parameter macro must also be passed explicitly to WCSim as a second argument. This file defines detector-level tuning parameters, such as water attenuation, Rayleigh scattering, cathode reflectivity, blacksheet reflection, and veto settings. If the default Hyper-K far detector tuning is used, the file can be taken directly from the WCSim installation inside the container:
\begin{lstlisting}[style=defstyle]
/opt/WCSim/install/macros/tuning_parameters_hkfd.mac
\end{lstlisting}
If this file needs to be modified, a custom version should be placed on the host system and bind-mounted inside the container, exactly as done for the user macro.
\subsubsection{WCSim macro}
The WCSim macro controls the detector geometry, PMT quantum efficiency, DAQ, dark noise, particle generator and output file. For the realistic Hyper-K ID-only geometry, the macro should contain:
\begin{lstlisting}[style=terminal]
/WCSim/WCgeom HyperK_HybridmPMT_IDonly_Realistic
/WCSim/Construct
\end{lstlisting}
The old geometry name:
\begin{lstlisting}[style=terminal]
/WCSim/WCgeom HyperK
\end{lstlisting}
is obsolete in the new WCSim build and causes WCSim to exit. WCSim explicitly suggests using one of the newer geometries, for example:
\begin{lstlisting}[style=terminal]
HyperK_HybridmPMT_WithOD_Realistic
HyperK_HybridmPMT_IDonly_Realistic
\end{lstlisting}
For the realistic Hyper-K geometry, the PMT quantum-efficiency method must be:
\begin{lstlisting}[style=terminal]
/WCSim/PMTQEMethod SensitiveDetector_Only
\end{lstlisting}
The older option:
\begin{lstlisting}[style=terminal]
/WCSim/PMTQEMethod Stacking_Only
\end{lstlisting}
is rejected by WCSim for this configuration.\\
A simple particle-gun setup for a positive muon is:
\begin{lstlisting}[style=terminal]
/mygen/generator gun
/gun/particle mu+
/gun/energy 120 MeV
/gun/direction 1 0 0
/gun/position 0 0 0
\end{lstlisting}
\subsubsection{Output ROOT file}
The output ROOT file is selected with:
\begin{lstlisting}[style=terminal]
/WCSimIO/RootFile /output_data/wcsim_HK_muplus_michel.root
\end{lstlisting}
This file is physically written in the host directory bound to \texttt{/output\_data}.


\section{fiTQun}
\label{sec:fitqun}

\subsection{Purpose of fiTQun}

fiTQun is a likelihood-based reconstruction package for water Cherenkov detectors. It reconstructs event-level quantities such as vertex position, particle direction, momentum, number of rings and particle identification. In this workflow, fiTQun is not used to simulate events. It reads WCSim ROOT files and reconstructs them.\\
The final workflow adopted here uses two separate images:
\begin{itemize}
    \item a dedicated WCSim image, built from the Hyper-K software base image and used only for event generation;
    \item a dedicated fiTQun image, derived from the official Hyper-K registry image and used only for reconstruction.
\end{itemize}
This separation avoids mixing two different software stacks in the same container and makes the role of each image clearer.
\subsection{Installation of fiTQun}
\subsubsection{Using the official fiTQun registry image}
\label{subsec:fitqun_registry_image}

The fiTQun image is taken from the private Hyper-K GitLab container registry:
\begin{lstlisting}[style=defstyle]
registry.git.hyperk.org/hyperk/recon/fitqun
\end{lstlisting}
Since this registry is private, authentication must be performed before pulling or building from the image:
\begin{lstlisting}[style=terminal]
apptainer registry login --username <USERNAME> docker://registry.git.hyperk.org
\end{lstlisting}
The login must be done outside the Apptainer definition file.\\
For reproducibility, the image should not be referenced only through the moving \texttt{latest} tag. The tested image corresponds to the following manifest digest:
\begin{lstlisting}[style=defstyle]
sha256:54e4856f12380b67853713f3992bac776292c36a6660fe54503131d9b688d490
\end{lstlisting}
The Apptainer definition file therefore starts from:
\begin{lstlisting}[style=defstyle]
Bootstrap: docker
From: registry.git.hyperk.org/hyperk/recon/fitqun@sha256:54e4856f12380b67853713f3992bac776292c36a6660fe54503131d9b688d490
\end{lstlisting}
The registry image already contains the installed fiTQun executable, ROOT, WCSimRoot, ToolFrameworkCore and the relevant Hyper-K software stack. In the tested image, the reconstruction executable is:
\begin{lstlisting}[style=terminal]
/usr/local/hk/fiTQun/install-Linux_x86_64-gcc_8-python_3.12.1/bin/runfiTQun
\end{lstlisting}
and the main software components are installed under paths of the form:
\begin{lstlisting}[style=terminal]
/usr/local/hk/ROOT/install-Linux_x86_64-gcc_8-python_3.12.1
/usr/local/hk/fiTQun/install-Linux_x86_64-gcc_8-python_3.12.1
/usr/local/hk/WCSimRoot/install-Linux_x86_64-gcc_8-python_3.12.1
/usr/local/hk/ToolFrameworkCore/install-Linux_x86_64-gcc_8-python_3.12.1
\end{lstlisting}
\subsubsection{WCSimRoot compatibility}
The fiTQun executable in this image is linked against WCSimRoot:
\begin{lstlisting}[style=terminal]
libWCSimRoot.so.1.12.29
\end{lstlisting}
whereas the independently built WCSim image used in this workflow contains a newer WCSimRoot version. This difference is not automatically fatal, but it is a compatibility point that must be kept in mind. The practical validation performed here showed that the WCSim ROOT file produced by the new WCSim image can be opened and reconstructed by the fiTQun image.

\subsubsection{Building a derived fiTQun image}
\label{subsec:fitqun_derived_image}

Instead of running the registry image directly with a long command, a derived Apptainer image is built. The goal is not to rebuild fiTQun itself, but to make the runtime environment cleaner and more reproducible. The derived image:
\begin{itemize}
    \item keeps the fiTQun installation from the official registry image;
    \item defines a small runtime setup script inside the image;
    \item downloads the Hyper-K tuning constants directly into the standard fiTQun constants directory;
    \item defines a \texttt{\%runscript} so that \texttt{apptainer run} automatically launches \texttt{runfiTQun}.
\end{itemize}
The runtime setup script is written during the build as:
\begin{lstlisting}[style=defstyle]
cat > /opt/setup_fitqun.sh <<'EOF'
#!/bin/bash

export FITQUN_ROOT=/usr/local/hk/fiTQun

export ROOT_INSTALL=/usr/local/hk/ROOT/install-Linux_x86_64-gcc_8-python_3.12.1
export FITQUN_INSTALL=/usr/local/hk/fiTQun/install-Linux_x86_64-gcc_8-python_3.12.1
export WCSIMROOT_INSTALL=/usr/local/hk/WCSimRoot/install-Linux_x86_64-gcc_8-python_3.12.1
export TOOLFRAMEWORKCORE_INSTALL=/usr/local/hk/ToolFrameworkCore/install-Linux_x86_64-gcc_8-python_3.12.1

export PATH="$ROOT_INSTALL/bin:$FITQUN_INSTALL/bin:$PATH"

export LD_LIBRARY_PATH="$ROOT_INSTALL/lib:$FITQUN_INSTALL/lib:$WCSIMROOT_INSTALL/lib:$TOOLFRAMEWORKCORE_INSTALL/lib:${LD_LIBRARY_PATH:-}"

export ROOT_INCLUDE_PATH="$WCSIMROOT_INSTALL/include/WCSimRoot:${ROOT_INCLUDE_PATH:-}"
EOF

chmod +x /opt/setup_fitqun.sh
\end{lstlisting}
The script manually defines the relevant paths instead of sourcing the full ROOT setup script. This is intentional: in the tested image, the ROOT setup script refers to a Geant4 installation path that is not present in the image. Defining the paths explicitly avoids this inconsistency and keeps the runtime environment minimal.\\
\newline
The \texttt{\%runscript} is:
\begin{lstlisting}[style=defstyle]
%runscript
    set -eo pipefail

    source /opt/setup_fitqun.sh

    exec runfiTQun "$@"
\end{lstlisting}
The runscript acts as the default command executed by \texttt{apptainer run}. It loads the fiTQun runtime environment and then forwards all user-provided arguments to the \texttt{runfiTQun} executable. It does not hard-code the input file, output file, number of events or parameter override file.

\subsubsection{Downloading fiTQun Hyper-K constants}
\label{subsec:fitqun_constants}

The fiTQun registry image contains the parameter override files and the helper scripts needed to download the tuning constants:
\begin{lstlisting}[style=terminal]
/usr/local/hk/fiTQun/sourceme_forHK
/usr/local/hk/fiTQun/getTuneFiles.sh
/usr/local/hk/fiTQun/HyperK_tune_files.list
\end{lstlisting}
The script \texttt{sourceme\_forHK} calls:
\begin{lstlisting}[style=terminal]
source getTuneFiles.sh HyperK_tune_files.list
\end{lstlisting}
and downloads the files listed in \texttt{HyperK\_tune\_files.list} into the fiTQun constants directory:
\begin{lstlisting}[style=terminal]
/usr/local/hk/fiTQun/const
\end{lstlisting}
In the derived image, these constants are downloaded at build time, so that they do not need to be bind-mounted from the host at runtime. The relevant part of the definition file is:
\begin{lstlisting}[style=defstyle]
echo "=== Download Hyper-K fiTQun constants into the standard const directory ==="

export FITQUN_ROOT=/usr/local/hk/fiTQun
export PATH="$FITQUN_ROOT:$PATH"

mkdir -p "$FITQUN_ROOT/const"
cd "$FITQUN_ROOT"

set +e
source ./sourceme_forHK
DOWNLOAD_STATUS=$?
set -e

if [ "$DOWNLOAD_STATUS" -ne 0 ]; then
    echo "ERROR: Hyper-K fiTQun constants download failed."
    exit "$DOWNLOAD_STATUS"
fi
\end{lstlisting}
The temporary \texttt{set +e} is necessary because the fiTQun download script first checks the MD5 checksum of each file before downloading it. For files that are not yet present, this first checksum check fails by design, and the script then proceeds to download the file. If \texttt{set -e} remained active during this step, the build would stop at the first missing file before the download could start.\\
After the download, the definition file checks that the main Hyper-K constants are present:
\begin{lstlisting}[style=defstyle]
test -f "$FITQUN_ROOT/const/fiTQun_scattablesF_HyperK.root"
test -f "$FITQUN_ROOT/const/angResp_HyperK_20inchBandL.root"
test -f "$FITQUN_ROOT/const/cPDFpar_20inchBandL.root"
test -f "$FITQUN_ROOT/const/11_tpdfpar_HyperK_20inchBandL.root"
test -f "$FITQUN_ROOT/const/13_tpdfpar_HyperK_20inchBandL.root"
test -f "$FITQUN_ROOT/const/211_tpdfpar_HyperK_20inchBandL.root"
test -f "$FITQUN_ROOT/const/CProf_11_fit_WCSim.root"
test -f "$FITQUN_ROOT/const/CProf_13_fit_WCSim.root"
test -f "$FITQUN_ROOT/const/CProf_211_fit_WCSim.root"
\end{lstlisting}
The downloaded constants include:
\begin{lstlisting}[style=terminal]
cPDFpar_20inchBandL.root
angResp_HyperK_20inchBandL.root
fiTQun_scattablesF_HyperK.root
fiTQun_scattable3d_HyperK.root
11_tpdfpar_HyperK_20inchBandL.root
13_tpdfpar_HyperK_20inchBandL.root
211_tpdfpar_HyperK_20inchBandL.root
CProf_11_fit_WCSim.root
CProf_13_fit_WCSim.root
CProf_211_fit_WCSim.root
\end{lstlisting}
These files are used by fiTQun to evaluate the likelihood terms related to charge, time, angular response, scattering and Cherenkov light profiles.

\subsubsection{Building the fiTQun image}
\label{subsec:building_fitqun_image}

After authenticating to the Hyper-K registry, the image is built with:
\begin{lstlisting}[style=terminal]
apptainer build fiTQun.sif fiTQun.def
\end{lstlisting}
If the system requires fakeroot privileges, the command becomes:
\begin{lstlisting}[style=terminal]
apptainer build --fakeroot fiTQun.sif fiTQun.def
\end{lstlisting}
The resulting image contains:
\begin{itemize}
    \item the official fiTQun installation from the registry image;
    \item the Hyper-K fiTQun constants under \texttt{/usr/local/hk/fiTQun/const};
    \item the runtime setup script \texttt{/opt/setup\_fitqun.sh};
    \item a runscript that launches \texttt{runfiTQun}.
\end{itemize}

\subsection{Running fiTQun}
\label{subsec:running_fitqun}

The WCSim output file must be made visible inside the fiTQun container through a bind mount. For example, if the host directory containing the WCSim output file is:
\begin{lstlisting}[style=terminal]
$(pwd)/WCSim_output_data
\end{lstlisting}
it can be mounted inside the container as:
\begin{lstlisting}[style=terminal]
/data
\end{lstlisting}

The reconstruction command is:
\begin{lstlisting}[style=terminal]
apptainer run \
  --bind "$(pwd)/WCSim_output_data":/data \
  fiTQun.sif \
  -n 1 \
  -p /usr/local/hk/fiTQun/ParameterOverrideFiles/HyperK.parameters.dat \
  -r /data/fiTQun.root \
  /data/WCSim_muplus_michel.root
\end{lstlisting}
The meaning of the main components is:
\begin{itemize}
    \item \texttt{--bind "\$(pwd)/WCSim\_output\_data":/data}: makes the WCSim input file visible inside the fiTQun container and writes the fiTQun output back to the same host directory.
    \item \texttt{fiTQun.sif}: is the derived fiTQun image.
    \item \texttt{-n 1}: processes one event.
    \item \texttt{-p /usr/local/hk/fiTQun/ParameterOverrideFiles/HyperK.parameters.dat}: selects the Hyper-K reconstruction parameter override.
    \item \texttt{-r /data/fiTQun.root}: selects the output ROOT file.
    \item \texttt{/data/WCSim\_muplus\_michel.root}: is the input WCSim ROOT file.
\end{itemize}
Since the Hyper-K constants are already stored inside the image, no additional bind mount to\\
\texttt{/usr/local/hk/fiTQun/const} is required. Since the runscript already loads the fiTQun runtime environment, no external shell script such as \texttt{fiTQun\_WCSim\_env.sh} is required either.\\
The output file contains a tree called:
\begin{lstlisting}[style=terminal]
fiTQun
\end{lstlisting}
which stores the reconstruction results.
